# corlinman 深度调研

日期：2026-07-22
研究对象：[`sweetcornna/corlinman`](https://github.com/sweetcornna/corlinman)
固定快照：`v1.36.1` / `2d51c5a05d13601bc5467fc0c68ab4768344f29c`

## 1. 结论先行

corlinman 已经不是“接一个大模型的 QQ 机器人”，而是一套自托管智能体平台：它把模型循环、QQ 等消息通道、会话、检索记忆、人格、工具、审批、沙箱、定时任务、管理后台与可观测性放进同一个系统。它最值得学习的不是某段提示词，而是把智能体当作长期运行的软件产品来治理。

但它也不应被原样照搬。项目规模大、迭代极快，兼容旧版本产生了一些不适合本项目的默认值。例如当前 `CORLINMAN_COMMAND_ADMINS` 未配置时，命令管理员检查会对所有调用者返回真。对“主人必须拥有最高权限、群友不能污染身份”的目标而言，我们必须使用默认拒绝、独立权限层和更严格的记忆写入策略。

因此推荐路线是：**参考并按需复用，不直接从整个上游分叉。** 先做一个窄而可靠的 QQ 智能体内核，确保身份、记忆和人格边界正确，再逐步扩展工具与多渠道。

## 4. 当前架构拆解

### 4.1 运行时

主栈为 Python：FastAPI/uvicorn 网关承接 HTTP、SSE 和后台；智能体循环、Provider、embedding、通道、插件等拆成多个 package；Next.js 提供管理台。工具可通过 JSON-RPC/gRPC 执行，并可放入 Docker 沙箱与人工审批门。

这个结构适合大型平台，但第一版没有必要复制 25 个以上的包。我们的 MVP 可以保留相同的逻辑分层，先运行在一个 Python 进程中，通过接口隔离，等确有性能或故障隔离需求再拆服务。

### 4.2 QQ 接入

corlinman 使用 NapCat 作为 QQ 客户端侧桥接，通过 OneBot v11 正向 WebSocket 接收事件并发送私聊/群聊消息。适配器负责重连、心跳、事件规范化、消息段处理和当前 `self_id` 识别；路由器再根据群白名单、@、关键词、命令、冷却时间与限流决定是否响应。

值得直接借鉴的设计：

- QQ 事件先规范化成统一 `InboundEvent`，业务层不直接依赖 NapCat JSON。
- 群白名单是硬门，@ 也不能绕过。
- 群聊默认 `mention_or_keyword`，没有关键词时等于仅响应 @。
- 私聊、群聊和不同发送者拥有不同的会话绑定。
- WebSocket 断线自动重连，队列有界，避免积压耗尽内存。

需要加强的地方：

- 主人身份必须来自传输元数据中的 QQ 号，不能从消息正文判断。
- 初期只允许一个测试 QQ、主人私聊和一个测试群；默认不读取所有群。
- 记录消息与主动回复分开开关，先做只读影子模式。

### 4.3 记忆

corlinman README 对外仍主要描述 SQLite 会话历史 + FTS5/BM25 知识库；v1.29 的统一记忆内核实际上更进一步：

- 热路径只记录一轮完成后的 observation，不在每条消息到来时做昂贵推理。
- 记忆项包含 tenant、user、persona 范围，以及来源、风险、置信度、重要度、信任、使用/矛盾次数和有效时间。
- `mk_recall_ledger` 记录每轮究竟注入了哪些记忆，便于解释错误和调整信任。
- 旧事实被新事实替代时失效而不删除，保留历史。
- FTS5/BM25 支持中文；还提供小规模向量余弦检索边界，但向量不是全部记忆。
- 高风险项先隔离再召回；persona 与用户范围有隔离测试。

这印证了一个关键判断：**向量库只是相似度检索手段，不是记忆治理本身。** 对本项目而言，可删除/失效/恢复、来源追踪和作用域比先上复杂向量数据库更重要。

### 4.4 身份与不同的人

上游把 `qq:<号码>` 等通道别名解析成内部不透明 UserId；不同通道默认视为不同人，只有经过运营者验证短语才能合并。会话和记忆再按 tenant、用户、persona 隔离。

本项目应采用同样的“外部身份映射到内部主体”方式，并额外定义不可由 LLM 修改的角色：`owner / admin / trusted / user / blocked`。主人 QQ 号只在部署时绑定，之后修改需要后台登录和二次确认。

### 4.5 人格与自我演进

上游把 Persona 的稳定描述与 mood、fatigue、recent topics 等运行状态分开保存；初次 seed 不覆盖已有状态，状态变化通过受控演进循环完成。它的 evolution/curator 会把用户纠正路由给受限后台智能体，后台智能体只允许修改技能与有限记忆文件，没有终端、网络和任意文件权限。

可借鉴的是“人格核心、软状态、技能、用户画像分层”。不可照搬的是让普通聊天纠正直接触发人格/技能写入：对于群聊环境，这会放大恶意诱导。本项目的自我演进第一版只产生提案，不自动生效。

### 4.6 管理与安全

上游拥有后台、工具审批、沙箱、日志、指标、健康检查、租户隔离、腾讯侧内容策略等成熟表面。但在主人权限方面存在一处明显不适用的兼容逻辑：管理员环境变量为空时 `is_command_admin()` 返回 `True`。我们必须反过来：主人未配置或配置不一致时，高权限命令全部失败，服务进入安全降级状态。

## 5. QQ 技术选型与现实风险

NapCat 是基于 NTQQ 的现代协议侧框架，接口面广且当前仍快速更新；其文档提供 OneBot 11 API。OneBot 适合隔离智能体与具体 QQ 实现，但 NapCat 文档也明确实现与停滞中的规范可能存在差异。另一个历史选项 Lagrange.Core 已在 2025-10-12 归档，现阶段不适合作为新项目主路径。

因此第一阶段建议 NapCat + OneBot v11，并做成可替换适配器。需要明确：这是第三方协议侧方案，而非把个人 QQ 完整能力视作稳定官方 API。由此推断它存在协议变化、登录限制和账号风控风险；必须使用测试小号、低频、白名单和版本固定，不能用主号直接进行高频自动化。

## 6. 许可证与复用边界

corlinman 使用 MIT 许可证，允许使用、修改、分发和商业化，但复制其代码或重要部分时必须保留原版权与许可证声明。NapCat 使用自己的混合许可，不能因为我们的项目选择某种许可证就忽略其上游限制；更安全的方式是把 NapCat 作为独立部署依赖，通过 OneBot 协议连接，不复制其内部代码。

项目代码许可证等真正开始写代码时再正式确定。若未来希望既开放又保留清晰的专利授权，可考虑 Apache-2.0；若按 MIT 代码直接复用，需要同时保留对应 MIT 声明。

## 7. 对本项目最有价值的十条经验

1. 先统一消息事件，再接多个通道。
2. QQ 群默认沉默，显式召唤才回复。
3. 原始会话、长期事实、任务承诺和人格核心是四类数据。
4. 每条长期记忆必须知道“谁说的、何时说的、在何处说的、为什么可信”。
5. 检索结果要记录注入账本，才能定位一次错误回答用了哪段记忆。
6. 主人权限由确定性代码判断，不能交给模型。
7. 人格核心版本化，软状态允许衰减，二者不能混写。
8. 工具权限独立于聊天权限，高风险动作需要批准。
9. 先做影子模式和攻击测试，再自动回复真实群聊。
10. 部署、升级、备份、健康检查与杀死开关都是产品功能。

## 8. 最终评价

corlinman 是非常好的“巨人肩膀”，尤其适合学习系统边界、长期记忆治理、QQ 路由与运维后台。它同时提醒我们：功能越多，兼容性和默认值越容易稀释安全边界。对你而言，最有价值的项目并不是再复制一个庞大平台，而是做出一个规模可控、权限不可混淆、记忆可审计、人格不漂移的个人智能体内核，再逐步长成全能助手。
